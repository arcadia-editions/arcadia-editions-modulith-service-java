# P-03 a Payment can stay AUTHORIZATION_REQUESTED for good after a crash during the processor call

status: decided A (person, 2026-11-20)
found by: review S1, reviewer (claude opus), 2026-11-20 (report .zenwave/handoff/place-order-flow/reports/review-S1.md)
flow: place-order-flow
blocks: none (no task depends on it; it keeps the flow from exiting)

## Problem
[payments-processing-domain-model.zdl:120-122](../../../arcadia-editions-modulith-api/payments-processing-domain-model.zdl#L120)
makes authorizePayment "creation only: no-op when a Payment for orderId exists, in any state" and commits
AUTHORIZATION_REQUESTED before the processor call. If the process dies (or is shut down) while the call is in
flight, AUTHORIZATION_REQUESTED stays committed, and the outcome is never saved. A republished OrderCreated is then a
no-op, getPaymentStatus answers STARTED
([place-order-flow.zfl:293-297](../../../arcadia-editions-architecture/business-flows/place-order-flow.zfl#L293)),
so the reservation timer releases nothing. The ZFL header promises "once payment has started, payment owns the end:
at most 3 attempts of at most 30 seconds"
([place-order-flow.zfl:62-65](../../../arcadia-editions-architecture/business-flows/place-order-flow.zfl#L62)), but
no command ends a Payment stranded in AUTHORIZATION_REQUESTED: the order and its stock are held forever.

## Evidence
Found by reading (T-48 code follows the ZDL): PaymentsProcessingServiceImpl.authorizePayment, interrupted wait at
shutdown throws and rolls back the outer transaction only. Not reproduced by a test (needs a crash/restart).

## Options
- A: accept for this iteration as a known limitation (as Kotlin T-84): ops resolve stranded AUTHORIZATION_REQUESTED
  payments by hand. Changes: none in models or code; a line in the ZFL header or an ADR.
- B: a redelivered OrderCreated (or reauthorizePayment's PaymentRetried) finds AUTHORIZATION_REQUESTED older than the
  processor timeout and ends it as FAILED processor_timeout with PaymentFailed, so the retry loop takes over. Changes:
  ZDL authorizePayment rule ("no-op in any state" becomes "except a stale AUTHORIZATION_REQUESTED"), a Payment
  `authorizationRequestedAt` field if none exists, regeneration, a fixture for a stale ORD-002-like payment; relies on
  Spring Modulith republishing incomplete events on restart.
- C: the reservation timer treats AUTHORIZATION_REQUESTED older than 30 s + margin as no payment and releases the stock.
  Changes: getPaymentStatus result semantics; payment and inventory then both act on the same order.

Recommendation: A now (demo iteration, no task blocked, same trade-off already accepted in Kotlin), B for the next
flow iteration: it keeps "payment owns the end" true without crossing contexts.

## Decision
A, accepted as a known limitation for this iteration (person, in the orchestrator session, 2026-11-20). No model or code change; ops resolve a Payment stranded in AUTHORIZATION_REQUESTED by hand. B stays a candidate for the next flow iteration.
